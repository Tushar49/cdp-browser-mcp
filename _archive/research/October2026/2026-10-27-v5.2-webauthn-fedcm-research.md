## 0. Cross-cutting correction (biggest finding of the cycle)

**Chromium now defines the per-target CDP surface via a generated config:**
`content/browser/devtools/protocol_config.json`
(<https://github.com/chromium/chromium/blob/main/content/browser/devtools/protocol_config.json>).

Pulls verified 2026-10-27:

- `Memory` domain: included with an explicit whitelist that **excludes
  `enable`/`disable`** — only `getBrowserSamplingProfile`,
  `setPressureNotificationsSuppressed`, `simulatePressureNotification`,
  `prepareForLeakDetection`, `getDOMCountersForLeakDetection` remain.
- `Performance`, `Ads`, `PWA` domains: **entirely absent** from the config
  (0 occurrences; `performance_handler.cc` no longer exists in
  `content/browser/devtools/` — replaced by `tracing_handler.cc`).
- `FindInPage`: brand-new domain added **Sep 28 2026**
  (commit `f445aa9`), methods `findFirst`/`findNext`/`findPrev` only — no
  `enable`.
- `Page` include list **does** contain `startScreenRecording`/
  `stopScreenRecording`.

## 1. WebAuthn domain

Source: devtools-protocol `browser_protocol.json` (master);
Chromium `content/browser/devtools/protocol/webauthn_handler.cc`,
`content/browser/webauth/authenticator_environment.cc`.

Surface (matches Playwright 1.65 protocol.d.ts, our local ground truth):
`enable{enableUI?}` / `disable`, `addVirtualAuthenticator{options}` →
`{authenticatorId}`, `removeVirtualAuthenticator`, `addCredential`,
`getCredential`, `getCredentials`, `removeCredential`, `clearCredentials`,
`setUserVerified{isUserVerified}`, `setAutomaticPresenceSimulation{enabled}`,
`setCredentialProperties{...}`, `setResponseOverrideBits{isBogusSignature?,
isBadUV?, isBadUP?}`; events `credentialAdded/Deleted/Updated/Asserted`.
Domain is **experimental**.

Hard ordering + validation rules (from handler source):

- `WebAuthn.enable` must be sent **before** `addVirtualAuthenticator`,
  else error `kVirtualEnvironmentNotEnabled` (webauthn_handler.cc:261).
- **Only one `internal`-transport authenticator may exist simultaneously
  per frame** (webauthn_handler.cc:304-309). Platform-authenticator
  semantics ride on `transport: "internal"`.
- Option-combination validation: `largeBlob`/`cmtgKey` require
  `hasResidentKey`; `credBlob`/`largeBlob`/`minPinLength` require CTAP2.1;
  `u2f`+`cable` invalid; `ctap2Version` default `ctap2_0`; ignored when
  protocol is `u2f`.
- `enableUI` defaults false; false is what stops the native WebAuthn UI
  from interfering — the automated-testing default.

Competitor exposure:

- **Puppeteer:** no high-level API at all (v25.16.0, zero
  `authenticator` hits in puppeteer-core src) — raw CDP only.
- **Playwright:** deliberately does NOT use the CDP domain. Since 1.61
  (2026-06-15) ships `browserContext.credentials` — an in-page-binding
  virtual authenticator (init script intercepting
  `navigator.credentials.create/get`, signs CBOR itself; `packages/playwright-core/src/server/credentials.ts`,
  <https://playwright.dev/docs/api/class-credentials>). Hides protocol/
  transport/CTAP2 versions, PRF, largeBlob; UV always succeeds.
  → most of the raw CDP WebAuthn surface is still novel vs Playwright.
- **chrome-devtools-mcp:** `configure_webauthn` (2026) — one idempotent
  tool: `enabled, protocol, transport, hasResidentKey,
  hasUserVerification, isUserVerified`. Hides credential CRUD, events,
  override bits, presence simulation, extensions.
  (<https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/src/tools/webauthn.ts>)

UNVERIFIED (needs live check in WS0): virtual authenticators on a REAL
attached user profile (expected to work — per-FrameTreeNode, standard
practice; but confirm on Brave 153 approval mode), and cross-tab/browser-wide
visibility of an authenticator created on one tab's session.

Live-test sites: **webauthn.io** (HTTP 200 verified 2026-10-27) for the full
signup/login round-trip.

## 2. FedCm domain + FedCM API status

Source: Chromium `content/browser/devtools/protocol/fedcm_handler.cc`;
devtools-protocol master; developer.chrome.com FedCM blogs.

Surface: `enable{disableRejectionDelay?}` / `disable`,
`selectAccount{dialogId, accountIndex}`, `clickDialogButton{dialogId,
dialogButton}`, `openUrl{dialogId, accountIndex, accountUrlType}`,
`dismissDialog{dialogId, triggerCooldown?}`, `resetCooldown`; events
`dialogShown{dialogId, dialogType, accounts[], title, subtitle?}`,
`dialogClosed{dialogId}`. DialogType: `AccountChooser|AutoReauthn|
ConfirmIdpLogin|Error`. Domain experimental.

Chromium semantics (the ones that shape the design):

- **Late-enable replays:** `FedCmHandler::DidShowDialog()` early-returns if
  not enabled (native dialog shows, no events, nothing queued) — BUT
  `Enable()` **replays `dialogShown` immediately** if a dialog is already
  live when the domain gets enabled. ⇒ a dialog open before we attached is
  recoverable by enabling and listening. (Kill the 5.1-era assumption that
  pre-attach dialogs are lost.)
- Popup-type dialogs (`kLoginToIdpPopup`, `kContinueOnPopup`,
  `kErrorUrlPopup`) are NOT exposed to automation (NOTREACHED in handler).
- Multi-IDP unsupported (crbug.com/328115461).
- `clickDialogButton(ConfirmIdpLoginContinue)` on an AccountChooser =
  "use another account".
- Dismissal can set an embargo (cooldown); `resetCooldown` clears it.
- `disableRejectionDelay` maps to `disable_delay_` — skips the promise
  rejection delay, right default for automation.

FedCM API status: default-on in Chrome since 108; Chrome 143 updates
(2026-01-12 blog) → structured JSON token responses, `.well-known/web-identity`
validation tightening, `accounts_endpoint` enforced from **Chrome 145**
(2026-02-10). Sources: developer.chrome.com/blog/fedcm-chrome-143-updates,
developers.google.com/identity/gsi/web/guides/fedcm-migration.

**Nobody automates FedCM dialogs**: Playwright only carries generated types +
a network.ts comment; Puppeteer has zero `FedCm` references;
chrome-devtools-mcp has no FedCM tool. Genuinely novel territory for 5.2.

Test setup: `fedcm-rp.glitch.me` / `fedcm-idp.glitch.me are **DEAD** (410,
verified 2026-10-27). Chrome-documented replacement:
**<https://fedcm-demo-rp.dev>** (200 verified; e.g. `/json-response` for the
structured-response demo). Accounts in the chooser come from real IdP logins
— seed by completing the IdP login once in the profile before automation.
UNVERIFIED: whether Brave 153 shows the dialog without settings changes
(Brave has historically gated FedCM behind privacy config — WS0 must verify
and try `brave://settings` paths before declaring the workstream dead).

## 3. Page.getAnnotatedPageContent

- Added 2025-11-22 (commit `a2401fd`); moved to embedder **2026-10-26**
  (commit `17d4573`): now implemented in `chrome/browser/devtools/protocol/
  page_handler.cc`, command takes `includeActionableInformation?: boolean`
  (default true → `ActionableAIPageContentOptions`), result
  `result.content` = base64 `AnnotatedPageContent` proto; "Not attached to
  an active page" on prerender; Android restricted to trusted clients.
- Underlying feature flag: `annotated-page-content-extraction`.
- **Proto: `components/optimization_guide/proto/features/common_quality_data.proto`**
  (~87KB; `message AnnotatedPageContent` at line 200). Top-level:
  `version`, `mode` (`DEFAULT=0|ACTIONABLE_ELEMENTS=1`), `root_node`
  (ContentNode tree, sparse DOM incl. iframe content), `main_frame_data`
  (FrameData), `page_interaction_info` (mouse position / focused element /
  a11y-focused id), `viewport_geometry`, `tab_id`, `popup_window`,
  `profile_information`. `ContentAttributes` oneof: text/image/svg/canvas/
  video/anchor/form/form_control/table/table_row/iframe/math +
  `common_ancestor_dom_node_id`, `geometry`, `annotated_roles` (AXRole
  list), `label`, `aria_role`, `is_ad_related`, `redaction_decision`.
  Geometry fully populated only in ACTIONABLE_ELEMENTS mode.
- Best public decode reference: Paul Irish's "distill-page" agent skill
  (<https://github.com/paulirish/dotfiles/blob/main/agents/skills/distill-page/scripts/proto/common_quality_data.proto>).
  ⚠️ cdproto's generated binding is stale vs the 2026-10-26 command shape.
- Field numbers are Chromium-internal — NOT a stable API. Any parser must
  treat the field map as advisory with a flat-extraction fallback (plan
  documents the wire-parser design but defers it to v5.3 — see plan §WS3).

## 4. Page.startScreenRecording / stopScreenRecording

- Added 2026-08-07 (commit `cc610ab`) → present in the Sept 2026 branch line;
  **Chrome/Brave 153 has it** (consistent with our live test).
- Signature: `startScreenRecording{ audio?, maxWidth?, maxHeight?, frameRate? }`
  → `{stream: IO handle}`; stop + drain via `IO.read`/`IO.close`; output
  container **MP4** (Chromium `media_recorder.cc`; matches our observed
  `ftyp` header). `audio` param exists (opt-in; likely needs mic permission).
- Puppeteer ships `page.record()` on this ("Works in Chrome 153+",
  `packages/puppeteer-core/src/cdp/ScreenRecording.ts`); chrome-devtools-mcp
  wraps it as `screencast_start/stop` (native MP4 path). Playwright does not
  use it (own screencast-frame path).
- Our 5.1 transient tab crash on attach: no public bug found (UNVERIFIED) —
  keep the experimental caveat.
